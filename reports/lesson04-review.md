### 🔸 顺带 1：既然忘记 `break` 这么危险，为什么 C 不让 `case` 自动 `break`？

（这个问题在你的"高危区"清单里被我列过。）

**三个原因，从历史到现实：**

1. **历史原因**：C 诞生于 1972 年，`switch` 的设计直接继承了更早的语言（B、BCPL）。
   那时候"贯穿"被视为**特性**而不是缺陷 —— 它能让多个分支共享代码，省内存（当时内存极贵）。
2. **C 的设计哲学**：**"信任程序员"**。C 从不替你做决定，也从不替你收拾东西。
   自动加 `break` 会打断"故意贯穿"这种用法，而语言设计者认为**你有权故意这么做**。
3. **如果自动 `break`，"共享代码"就得多发明一套语法** ——
   而现在只需要把 `case` 标签连写就行，反而更简洁。

**所以现在怎么做？** 用工具补上这门语言的"不体贴"：

- 用 clang 的 `-Wimplicit-fallthrough`（讲义里那个开关），让编译器替你盯着；
- **写注释标注**：`/* fall through */` —— 让下一个读代码的人知道"这不是 bug"；
- **纪律**：每个 `case` 后面要么有 `break`，要么有说明。

> 这也回答了一个更大的问题：**"语言不帮我的地方，我用工具和纪律补上。"**
> 这是职业程序员和业余爱好者最大的区别之一。

### 🔸 顺带 2：浮点比较的容差 `0.000001` 是怎么定出来的？为什么不用更小的数？

（这个问题也在"高危区"清单里。）

**先说结论：`1e-6` 是个经验值，不是定律。** 严格的做法要考虑"数值的量级"。

**本机实测的两个关键数字：**

```text
DBL_EPSILON = 2.2204460492503130808e-16   ← double 能分辨的最小相对差值
DBL_DIG     = 15                          ← double 的十进制有效位数
```

**怎么理解：**

- `DBL_EPSILON ≈ 2.22e-16`：意思是**在 1.0 附近**，double 能分辨的最小间隔是 `2.22e-16`。
  比这更小的差别，double **根本存不下来**。
- `DBL_DIG = 15`：double 大约有 **15~17 位十进制有效数字**。所以第 16 位以后的比较没有意义。

**为什么 `1e-6` 够用（在这个例子里）：**

```text
真实差值 |0.1+0.2 - 0.3| ≈ 4.4e-17     ← 比 1e-6 小得多，所以判"相等" ✓
```

`4.4e-17` 只有 `1e-6` 的一千亿分之一，所以 `1e-6` 这个"门槛"足够宽松，
而且**远大于** double 的噪音（`2.22e-16`），不会误判。**它卡在"噪音之上、误差之下"的舒适区。**

**但严格来说，`1e-6` 有个隐患**：它是**绝对容差**。
如果两个数本身是 `1e20` 量级的，那么 `1e-6` 就毫无意义了（那个量级下噪音都比它大）。

**专业写法是"相对容差"**：

```c
#include <math.h>       /* fabs */
#include <float.h>      /* DBL_EPSILON */

int nearlyEqual(double a, double b)
{
    double diff = fabs(a - b);
    double scale = fabs(a) > fabs(b) ? fabs(a) : fabs(b);
    if (scale < 1.0) { scale = 1.0; }          /* 避免 a、b 都接近 0 时除出问题 */
    return diff <= DBL_EPSILON * scale * 8;    /* 乘以 8 是留点余量 */
}
```

**这一段现在看不懂完全正常**（用到了函数、指针、`math.h`，都是后面的内容）。
你只需要记住一句话：

> **绝对容差（如 `1e-6`）够用的情况是"你知道数值大概在什么量级"；
> 一旦量级跨度大，就得用相对容差。而无论哪种，都绝不要用 `==`。**
