这是很典型的"边界思维"，写真实代码时非常值钱。

**思考题答案（正确）**：

> 发现因子说明不是质数，没必要继续循环了，所以 break。
> 如果 n = a × b 且 a ≤ b，那么 a * a <= n，所以 a 最大只能是 √n。

**推理完全正确。** 我把措辞补完整一点，方便你以后讲给别人听：

- **为什么可以 break**：质数的定义是"只有 1 和它自己两个因子"。
  一旦找到一个位于 `2 ~ n-1` 的因子，这个数就**已经不可能是质数**了，
  继续试下去**不会改变结论**，所以立刻收工。
- **为什么只需试到 √n**：假设 `n = a × b` 且 `a ≤ b`，那么 `a × a ≤ a × b = n`，
  即 `a ≤ √n`。所以**如果 n 有因子，必定存在一个 ≤ √n 的因子**；
  试完 `2 ~ √n` 都没找到，更大的区间也不可能有。
  代码里写 `i * i <= number` 就是为了**不用 `<math.h>` 的 `sqrt()`**（避免浮点误差和额外头文件）。

**顺便算一下这道题的"效率账"**（这是"算法复杂度"的第一次直观感受）。
我实测统计了 2~100 范围内两种做法的**总试除次数**：

| 做法 | 2~100 的总试除次数 | 倍数 |
| --- | --- | --- |
| 试到 `n - 1` | **4851 次** | 1× |
| 试到 `√n` | **525 次** | **快 9.2 倍** |

**在 2~100 这个范围就已经差 9 倍了。** 数据量越大差距越夸张 ——
比如 n 是 100 万时，`n-1` 要试 100 万次，`√n` 只要 1000 次，**差 1000 倍**。
这就是"算法复杂度"的第一次直观感受：**同一个问题，好的算法能快几个数量级。**

### 🔸 顺带 1：为什么编译器不警告死循环？

（这是你清单里列的第一类疑问。）

**先给结论：不是编译器"偷懒"，而是这件事在数学上就不可能完全做到。**

**第一层：停机问题（不可判定）**

1936 年图灵证明了：**不存在一个通用算法，能判断"任意给定程序是否会在有限步内停下"**。
所以"完美检测所有死循环"这个目标，**从原理上就不可能实现**。

**第二层：那编译器为什么连"变量没变"都看不出来？**

因为编译器看到的只是一个函数，它无法确定变量的值会不会被**别的代码**改变：

```c
while (i < 5) {
    printf("%d ", i);
    maybeChangeI(&i);       /* 这个函数可能改了 i，也可能没改 —— 编译器看不到它的内部 */
}
```

编译器只能看到当前这个编译单元。只要 `i` 的地址被传出去过，
它就再也不能假设"`i` 没被人改过"。所以**不做这种判断，反而是正确的保守做法**。

**第三层：那编译器究竟能帮我检查什么？**

它只能做**局部、确定**的检查。本课你已经见过两个：

| 编译器能查的 | 触发条件 | 本课实测 |
| --- | --- | --- |
| `-Wempty-body` | 循环体**字面上**是空的（`for (...);`） | ✅ 警告了 |
| `-Wparentheses` | 条件**字面上**是赋值（`while (i = 5)`） | ✅ 警告了 |

它**不能**查的：变量是否朝着"条件变假"的方向走 —— 那需要全局推理。

**所以"防止死循环"这件事，责任在你自己**，本课那条纪律就是这个意思：

> **每个循环都必须有人负责让条件变假。**

配合两个实用手段：
1. **三要素检查**（初始化 / 条件 / 更新）；
2. **真跑一遍**（编译器不说的，运行时会说 —— 只是它说的方式是"停不下来"，而不是报错）。

> 🔧 **再补一个实用技巧**：以后循环出问题，最简单的调试手段是
> **在循环体里临时加一行 `printf`**，打印控制变量的值：
> ```c
> while (i < 5) {
>     printf("[debug] i = %d\n", i);      /* 看它到底在涨、还是卡住了 */
>     ...
> }
> ```
> 如果打印出来永远是同一个值，死循环的原因立刻现形。
> 第 6 课后我们会学更好的工具（函数 + 断点调试），但"打印大法"永远管用。

### 🔸 顺带 2：`for` 和 `while` 到底什么时候用哪个？

（这也是你清单里的一条。）

**没有硬性规定，但有一条很好用的经验法则：**

> **循环次数"事先知道"→ 用 `for`；循环次数"取决于条件"→ 用 `while`。**

| 场景 | 选谁 | 为什么 |
| --- | --- | --- |
| 遍历 1~100、数组下标 0~n-1 | **`for`** | 次数已知，三要素写在一行，最不容易漏更新 |
| 读到输入 0 为止（`task1`） | **`while`** | 不知道要读几次，取决于用户输入 |
| 拆数字 `while (n > 0)` | **`while`** | 次数取决于数字有几位 |
| 至少执行一次（输入校验） | **`do-while`** | 先读一次才知道合不合法 |
| 求最大公约数、链表遍历 | **`while`** | 次数由条件决定 |

**再补三条实践共识：**

1. **能用 `for` 就用 `for`** —— 因为它把"更新语句"焊在了头部，
   **从结构上就防住了"忘记 i++"这个头号死循环原因**；
2. **`while (1)` 不是坏味道**，但必须满足两个条件：
   ① 循环体里**一定有一条能到达的 `break`**；② 加注释说明"为什么用无限循环"。
   你的 `task1` 就是标准写法（用 `break` 在读到 0 时退出）✓；
3. **`while` 里的 `continue` 要格外小心** —— 因为 `while` 没有"头部更新"，
   `continue` 可能把唯一的更新语句跳过（本课报错速查第四节实测过）。

**最后一句总结**：
> **`for` 是"我知道要走几次"，`while` 是"走到条件不成立为止"。**
> 拿不准的时候问自己："这个循环，我事先知道要转几圈吗？"
