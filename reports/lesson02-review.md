### ❓疑问 1：C 语言还有其它基本数据类型吗？（`byte` / `short` / `long` / `boolean` 等）

**答案：有，而且不少。给你一张完整地图。**

👉 **我把它们全做成了一个可以直接运行的示例：[examples/07_qa_all_types.c](../lessons/lesson02/examples/07_qa_all_types.c)**
（实测 0 错误 0 警告，用 `⌘⇧B` 编译、任务②运行即可看到下面整张表）

**C 的基本类型总共有 4 大家族：**

```text
基本类型（C17 标准 6.2.5）
├── 1. 整数类型
│   ├── char / signed char / unsigned char          ← 1 字节
│   ├── short / unsigned short                      ← 2 字节
│   ├── int / unsigned int                          ← 4 字节（最常用）
│   ├── long / unsigned long                        ← 8 字节
│   ├── long long / unsigned long long              ← 8 字节
│   └── _Bool（C99 起）                              ← 1 字节，存 0/1
├── 2. 浮点类型
│   ├── float        ← 4 字节
│   ├── double       ← 8 字节（日常就用它）
│   └── long double  ← 本机也是 8 字节（见下方备注）
├── 3. 枚举类型 enum                    ← 第 11 课讲
└── 4. void（"没有类型"）                ← 只用于函数返回值/参数
```

**你提到的三个名字，逐个澄清：**

| 你说的 | C 里有吗 | 说明 |
| --- | --- | --- |
| `byte` | ❌ **没有** | 那是 Java / C# 的叫法。C 里想表达"1 字节无符号"，用 `unsigned char` 或 `uint8_t` |
| `short` / `long` | ✅ **有** | 见上表，`short`=2 字节，`long`=8 字节（macOS 64 位） |
| `boolean` | ⚠️ **原本没有** | C99 起有了 `_Bool`；`#include <stdbool.h>` 后就能写 `bool` / `true` / `false`（本质就是 `_Bool` 的别名） |
| `String` | ❌ **没有** | C 的字符串是"char 数组"，第 8 课专门讲 |

**本机实测的全部类型（摘自 `07_qa_all_types.c` 的真实输出）：**

| 类型 | 字节 | `printf` 格式符 | 取值范围 |
| --- | --- | --- | --- |
| `_Bool` / `bool` | 1 | `%d` | 0 或 1 |
| `char` | 1 | `%c` / `%d` | `'A'`=65 |
| `signed char` | 1 | `%hhd` | −128 ~ 127 |
| `unsigned char` | 1 | `%hhu` | 0 ~ 255 |
| `short` | 2 | `%hd` | −32768 ~ 32767 |
| `unsigned short` | 2 | `%hu` | 0 ~ 65535 |
| `int` | 4 | `%d` | −2147483648 ~ 2147483647 |
| `unsigned int` | 4 | `%u` | 0 ~ 4294967295 |
| `long` | 8 | `%ld` | −9.2e18 ~ 9.2e18 |
| `unsigned long` | 8 | `%lu` | 0 ~ 1.8e19 |
| `long long` | 8 | `%lld` | 同 `long` |
| `unsigned long long` | 8 | `%llu` | 0 ~ 1.8e19 |
| `float` | 4 | `%f` | 约 7 位有效数字 |
| `double` | 8 | `%f` | 约 15–17 位有效数字 |
| `long double` | **8** ⚠️ | `%Lf` | **本机和 double 一样大！** |

**格式符的"长度修饰符"规律**（这个是关键，记住就能自己推导）：

| 修饰符 | 含义 | 例子 |
| --- | --- | --- |
| `hh` | 比 int 还短的整数（char 级） | `%hhd` `%hhu` |
| `h` | short 级 | `%hd` `%hu` |
| （无） | int 级 | `%d` `%u` |
| `l` | long 级（浮点里表示 double 的输入） | `%ld` `%lu` `%lf` |
| `ll` | long long 级 | `%lld` `%llu` |
| `L` | long double | `%Lf` |
| `z` | size_t（`sizeof` 的结果） | `%zu` |
| `j` | intmax_t | `%jd` |

**两条实用建议：**

1. **日常写代码**：`int`（整数）、`double`（小数）、`char`（字符）就够了 —— 别一上来就用 `long long`；
2. **需要精确控制宽度时**（跨平台、读写二进制文件、网络协议）：用 `<stdint.h>` 里的**定长类型**
   `int8_t` / `int16_t` / `int32_t` / `int64_t` / `uint32_t`，名字里就写着几位。

**想查极限值**：`#include <limits.h>` 有 `INT_MAX`、`SCHAR_MIN` 等；`#include <float.h>` 有 `DBL_MAX` 等。
**想知道某类型几字节**：`sizeof` 去问，**永远不要死记** ——
上面 `long double` 在本机是 8 字节就是活生生的例子（在 x86 Linux 上它通常是 16 字节）。

### ❓疑问 2：`%.2f` 说好四舍五入，为什么 `0.125 → 0.12`、`0.1245 → 0.124`？

**这是本课最精彩的问题，也是绝大多数人一辈子都没搞清的问题。**
你的观察完全正确：**`printf` 的舍入规则不是简单的"四舍五入"**。原因是**两个不同的机制**，你恰好各踩了一个。

👉 **完整实验代码：[examples/08_qa_rounding.c](../lessons/lesson02/examples/08_qa_rounding.c)**（0 错误 0 警告，可直接跑）

#### 真相第一步：`double` 里存的，往往不是你以为的那个数

`double` 只有 64 位，**只能精确表示"分母是 2 的幂"的分数**（如 1/2、1/4、1/8）。
像 `0.1`、`0.1245` 这种十进制小数，**大多数根本存不进去**，只能存一个最接近的值。

我把内部真相打印出来了（`%a` 是十六进制浮点格式，能原样显示存的二进制值）：

```text
0.125  = 0.12500000000000000000   %a = 0x1p-3              ← 精确等于 1/8，存得下！
0.1245 = 0.12449999999999999956   %a = 0x1.fdf3b645a1cacp-4 ← 实际比 0.1245 小！
0.135  = 0.13500000000000000888                            ← 实际比 0.135 大
0.145  = 0.14499999999999999001                            ← 实际比 0.145 小
```

**看第二行**：`0.1245` 实际存的是 `0.12449999999999999956`，**比一半小一点点**。
所以 `%.3f` 时它压根**没到"一半"**，直接舍去 → `0.124`。
**这不是"没四舍五入"，而是"它没到进位线"。**（你的第一个例子，属于机制 A）

#### 真相第二步：真到了"正好一半"时，`printf` 用的是"向偶数舍入"

`0.125` 是能**精确存储**的（`0x1p-3` = 1/8），所以 `%.2f` 时它**正好卡在 0.12 和 0.13 的正中间**。
这时候 C 的标准做法（glibc/macOS 采用 IEEE 754 默认舍入模式）是：
**进位到"末位是偶数"的那一边**，也就是"**四舍六入五成双**"（银行家舍入）。

**证据（真实输出）：**

```text
先看最好懂的整数例子（%.0f）：
  1.5 → 2      2.5 → 2      3.5 → 4
                  ↑ 2.5 没有进位成 3，而是变成了 2（2 是偶数）

再看小数（%.2f，这些值都能被 double 精确存储）：
  0.125 → 0.12    0.375 → 0.38    0.625 → 0.62    0.875 → 0.88
        ↑ 在 0.12/0.13 之间选 0.12（2 是偶数）
```

**你问的第二个例子，就是机制 B**：`0.125` 是精确的一半 → 选了偶数末位 `0.12`。

#### 一句话对照（贴在你的笔记里）

| 你写的 | 实际存的 | 属于哪种情况 | 结果 |
| --- | --- | --- | --- |
| `0.1245` | `0.1244999...` | 机制 A：没到一半 | `0.124` |
| `0.125` | 精确的 `0.125` | 机制 B：正好一半 → 向偶数 | `0.12` |
| `0.135` | `0.1350000...888` | 超过一半 → 正常进位 | `0.14` |
| `0.145` | `0.1449999...001` | 没到一半 → 舍去（**最著名的坑**） | `0.14` ⚠️ |

#### 工程结论（这三句话比答案本身更值钱）

1. **永远不要用 `double` 做"必须精确"的事**。
   金额一律**用整数存"分"**（`1990` 表示 19.90 元）——这是银行和电商的通行做法。
2. **永远不要用 `==` 比较两个 `double`**。
   `0.1 + 0.2 == 0.3` 在 C 里是**假**的（不信你可以试着打印 `%.20f` 看看）。
   正确做法是比较差值：`差值 < 0.000001` 就算相等。
3. **打印结果取决于"它实际存了多少"，而不是"你写了多少"**。
   所以"我明明写了 0.1245" 这种想法，在浮点世界里不成立。

> 📌 顺便说明严谨性：C 标准把"最后一位怎么舍入"留给具体实现，
> 我上面所有的结论都是**在你这台机器上实测**出来的（Apple clang + macOS），
> 换个平台理论上可能不同 —— 所以**更不该依赖**它。
